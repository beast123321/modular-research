# Modular Research v1.2.0 TikTok Provider Verification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release v1.2.0 by hard-bounding TikTok live validation at 12 calls and promoting only TikTok capabilities backed by a successful real Provider response plus successful normalizer execution.

**Architecture:** Reuse the existing provider-neutral `live_validation.py` harness and Endpoint Registry. Add one deterministic verification-promotion layer that converts a redacted live-validation report into a sanitized verification manifest and optional registry metadata updates; it must never infer endpoint-exact pricing from provider-default budget estimates. The final release is evidence-gated: code can be prepared offline, but registry promotion, release metadata, and v1.2.0 claims happen only after an explicitly approved paid TikHub validation run.

**Tech Stack:** Python >=3.10, stdlib JSON/argparse/pathlib/datetime/unittest, existing TikHub transport/normalizers/EndpointRegistry, GitHub Actions Python 3.10/3.12/3.13.

**Spec:** `docs/superpowers/specs/2026-08-26-modular-research-v2-design.md`

## Global Constraints

- Skill remains independent of HCO, Hermes, Shopify, and any specific Agent runtime.
- TikTok live validation has a hard ceiling of 12 Provider calls in both CLI and programmatic runner paths.
- Real network execution still requires explicit `--execute`, `--yes`, and a sufficient `--max-budget-usd`.
- CI remains offline, receives no TikHub API key, and makes no paid requests.
- A capability may become `live_verified` only when the live-validation report contains an actual successful Provider result for that capability and the normalizer completed successfully for that result.
- Capabilities not successfully called in the approved live run must retain their pre-run verification status.
- Provider-default budget estimates must never be written as endpoint-exact `unit_price_usd` evidence.
- Raw Provider responses, API keys, `config.json`, and live-validation run directories must not be committed.
- Existing Douyin v1.1.3 verification metadata and its six live-verified capabilities must remain unchanged.
- Existing TikTok/Douyin planner, executor, normalizer, analysis, and legacy behavior must remain backward compatible unless this plan explicitly changes it.

- [ ] **Step 4: Implement the shared ceiling helper and use it in CLI + runner**

```python
LIVE_VALIDATION_CALL_CEILINGS = {"douyin": 6, "tiktok": 12}


def clamp_call_ceiling(platform: str, requested: int | None) -> int:
    key = str(platform).strip().lower()
    ceiling = LIVE_VALIDATION_CALL_CEILINGS[key]
    if requested is None:
        return ceiling
    return max(0, min(ceiling, int(requested)))
```

`LiveValidationRunner.run()` clamps before calculating estimated cost or entering the queue loop. `main()` uses the helper for both platforms.

### Task 2: Add evidence-gated TikTok verification promotion

**Files:**
- Create: `scripts/provider_verification.py`
- Modify: `scripts/test_phase12_tiktok_provider_verification.py`

**Interfaces:**
- Produces `build_verification_manifest(report: dict, *, platform: str) -> dict`.
- Produces `apply_registry_promotions(report: dict, registry_path: Path, *, platform: str) -> dict`.
- CLI accepts `--report`, `--platform`, optional `--registry`, optional `--manifest-out`, and `--apply`.
- Default CLI is dry-run: print the sanitized manifest and do not modify the registry.
- A promotable result row must have `status == "ok"`, a Provider response represented by the live runner, and a `normalizer_counts` dictionary (normalizer completed without exception).
- The manifest contains only verification metadata, never raw Provider payloads or response bodies.
- Registry mutation may change verification metadata only: `status`, `verified_at`, `verification_basis`, `validation_calls`, `normalizer_validation`. It must preserve `method`, `path`, `request_location`, `unit_price_usd`, defaults, limits, and existing pricing provenance.
